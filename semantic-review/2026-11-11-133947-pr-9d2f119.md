# Require login to create a product

Product creation was previously the one write endpoint that anonymous callers could reach; this commit closes that gap. `POST /api/products` now sits behind `requireAuth`, the frontend only renders the add-product form for logged-in users, and the empty state nudges anonymous visitors to log in instead of inviting them to add a product. Tests were updated to send a token when creating products and a new case asserts that an anonymous POST is rejected with 401 and persists nothing. The change brings product creation in line with the deletion and note-creation endpoints, which already required a login.

Watch for: nothing blocking. One minor UX inconsistency (confirmed) — the name-search box stays visible to anonymous users while the create form disappears, which is intentional per the existing public-search design, not a regression.

**Verdict**: APPROVED

## High-level view

The backend gating is a one-line addition of the shared `requireAuth` handler to `POST /api/products`, placed consistently with the existing `DELETE /:productId` and `POST /:productId/notes` routes. Authentication runs before any body parsing or persistence, so anonymous callers get a 401 and nothing is written. The 401 body (`{ error: 'Authentication required' }`) comes from the same middleware every other protected route uses, so the contract is uniform.

The read surface is untouched: listing (`GET /`), name search (`GET /search` for anonymous), single-product view, and note listing all remain public. Only the write path changed, so the anonymous browse-and-read flows are preserved.

On the frontend, the form is gated behind the existing `user` flag from `useAuth()`, the same signal that already gates product deletion and advanced search. The empty-state copy branches on the same flag so anonymous visitors see a "log in to add" message instead of a dead instruction to use a form they can't see.

Test coverage is solid: the shared helpers now authenticate before creating products, a dedicated backend case asserts the 401-and-no-write behavior, and a frontend case asserts the form is absent for anonymous visitors. Backend product suite passes (75 tests).

### Gating the create route

`POST /api/products` now takes `requireAuth` as middleware (`backend/src/routes/products.ts:37`), matching the pattern already used by `DELETE /:productId` (line 50) and `POST /:productId/notes` (line 63). Because `requireAuth` runs before `parseProductName`, an anonymous caller is rejected before any validation or write happens — the new backend test confirms the product list stays empty after a rejected POST (`backend/test/products.test.ts:36-42`). The 401 body is `{ error: 'Authentication required' }`, produced by `createAuthMiddleware` via `MESSAGES.authenticationRequired` (`backend/src/auth/middleware.ts:38`, `backend/src/errors.ts:23`), so the error contract matches every other gated route.

No route was left unintentionally open. The remaining public routes — `GET /`, `GET /search` (with `optionalAuth` guarding advanced filters), `GET /:productId`, `GET /:productId/notes` — are all reads and were already public by design. The only state-changing routes (`POST /`, `DELETE /:productId`, `POST /:productId/notes`) are now uniformly behind `requireAuth`.

### Frontend form gating

The add-product form renders only when a user is present: `{user && <ProductForm onCreate={handleCreate} />}` (`frontend/src/pages/ProductListPage.tsx:71`). This reuses the `user` value from `useAuth()` that already gates the per-product delete control (line 157) and the advanced-search toggle (`canUseAdvanced={Boolean(user)}`, line 111), so the gating signal is consistent across the page. The empty-state copy branches on the same flag (lines 139-144), swapping the "add your first one above" instruction for "Log in to add the first one" when anonymous — a worthwhile touch, since the previous copy pointed at a form that no longer exists for those visitors.

One asymmetry worth noting: the name-search box (`ProductSearch`) stays visible to anonymous users while the create form disappears. That is deliberate — the component is explicitly designed so name search is public and only advanced filters are gated (see the comment at `ProductListPage.tsx:41-43` and the backend `/search` handler) — so this is not a regression, just an asymmetry a reviewer might otherwise question.

### Test coverage

The shared helper `createProduct` now resolves an auth header and sends it (`backend/test/helpers.ts:33-37`), so every downstream test that seeds products through it exercises the authenticated path. The dedicated new case asserts both halves of the gate — a 401 with the exact error body, and that nothing was persisted (`backend/test/products.test.ts:36-42`). The cross-cutting auth test was renamed and flipped from asserting product creation stays open to asserting it returns 401 (`backend/test/auth.test.ts:334-340`), keeping the note-edit assertion alongside it.

The frontend adds a case asserting the form controls are absent for anonymous visitors and the log-in empty-state message is shown (`frontend/src/pages/ProductListPage.test.tsx:121-129`), and the existing creation tests now call `signIn('alice')` before rendering so they continue to exercise the authenticated flow. The local `createAs` helper in the backend product suite resolves the header before issuing the request, matching the existing note-helper convention of not leaving a supertest request pending across an await.

Not tested: there's no frontend assertion that `api.createProduct` attaches the token, but that behavior lives in the API client and is covered by its own tests; it's not introduced by this change.

### Security posture

The change tightens the trust boundary: the last anonymous write endpoint is now authenticated, and auth runs before body parsing so a rejected request touches no persistence. No new credential handling, token logic, or transport was introduced.
