# Author-only note editing with persisted note authorship

This change restricts `PUT /api/notes/:noteId` to authenticated users and, going one step beyond the literal ask, to the user who authored the note. To enforce that, it persists a note's author: a nullable `author_id` column is added to the `notes` table, the creating user is recorded on note creation, and the author id is surfaced on the `Note` payload as `author`. The frontend decodes the numeric user id from the JWT `sub` claim so it can compare `user.id` against `note.author` and show the Edit control only on the viewer's own notes. Pre-feature notes become "authorless" (`author_id IS NULL`) and are treated as editable by nobody — the same 403 outcome as a note owned by someone else. The whole thing is backed by a spec under `.kiro/specs/notes-edit-auth` whose design resolves the three deferred decisions (authorless → 403, additive `ALTER` migration, numeric `users.id` as the shared identifier).

Watch for: delete is not author-gated — any logged-in user can delete any note, including notes they don't own (confirmed, `backend/src/routes/notes.ts`). This may be intentional per the spec's scope (Requirement 2 covers edit only), but it's an asymmetry with edit worth a conscious decision. Everything else lines up with the spec and is well tested.

**Verdict**: APPROVED

## High-level view

Authorship is persisted with a nullable `author_id` FK to `users`, added to the fresh `CREATE TABLE` and backfilled onto pre-feature databases by `migrateNotesAuthor`, which guards the `ALTER` behind a `PRAGMA table_info` check so startup stays idempotent. Legacy rows keep `NULL`, the honest representation of an unknown author.

The edit gate lives in the route: `requireAuth` runs before the note lookup so anonymous callers get a uniform 401 with no signal about which note ids exist, then a single `note.author !== req.user.id` comparison enforces ownership. That one comparison also refuses authorless notes for free, since `null` never equals a numeric user id — a 403, not a 404, matching the design's conservative decision.

The shared identifier is the numeric `users.id`, already signed into the token as `sub`. No server token change was needed; the frontend `decodeSession` now parses `sub` into a number and rejects tokens whose `sub` is missing or non-numeric, exactly as it already rejects a missing `username`. `ProductDetailPage` passes `onSave` only when `user.id === note.author`, and `NoteItem` makes `onSave` optional and hides Edit when it's absent, mirroring the existing `onDelete` gating. The frontend gate is convenience only; the backend remains the real gate.

The one gap is on delete: `DELETE /api/notes/:noteId` requires authentication but performs no ownership check, so any logged-in user can delete any note. The spec scopes author-only to edit, so this is plausibly deliberate, but it leaves edit and delete with different trust models on the same resource.

### Nullable `author_id` and the idempotent migration

The column is `author_id INTEGER REFERENCES users (id)` — deliberately nullable, with no `NOT NULL DEFAULT`, because legacy rows have no truthful author to backfill. Pre-feature databases get it from `migrateNotesAuthor`, which reads `PRAGMA table_info(notes)` and only runs the additive `ALTER TABLE ... ADD COLUMN` when the column is absent, so calling it on every `openDatabase` is idempotent.

One subtlety worth noting: the `REFERENCES users (id)` clause on `ALTER ADD COLUMN` constrains future rows only — SQLite does not retro-validate existing rows, and legacy rows hold `NULL`, which satisfies a nullable FK regardless. No row is rewritten or removed. The migration test in `backend/test/database.test.ts` constructs a genuine pre-feature table (drops and recreates `notes` without `author_id`), inserts two rows, then asserts the column shape, the FK entry, that both rows survive with `author_id = NULL`, that a second call is a no-op, and that reopening the file through `openDatabase` is also a no-op — a thorough exercise of Requirement 3.4.

### Edit gate: auth before lookup, single ownership comparison

```
anonymous PUT ──► requireAuth ──► 401 (lookup never runs, no id-existence leak)
authed PUT    ──► requireAuth ──► requireNote ──► 404 if missing
                                               └► note.author !== req.user.id ──► 403
                                                  else ──► notes.update ──► 200
```

Ordering `requireAuth` before `requireNote` is what makes the 401 uniform: an unauthenticated `PUT` to an existing note and to a missing note return identical responses, which `notes.test.ts` asserts directly ("no existence leak"). Only after authentication does a missing note produce 404.

The ownership check `if (note.author !== req.user!.id)` collapses "different author" and "authorless" into one 403 path — `note.author` is `null` for a legacy note, never equal to a numeric user id. The response is 403 rather than 404, so a non-author is told the edit is refused, not that the note is missing. The suite covers both a cross-user property test (100 runs, user B editing user A's note → 403, content unchanged) and an explicit authorless-note edge (→ 403, stored note unchanged).

### Delete trust model differs from edit

`DELETE /api/notes/:noteId` was updated in an earlier change to require authentication, but this change does not add an ownership check to it. The result is that any authenticated user can delete any note — their own, another user's, or an authorless one — while editing those same notes is forbidden. The spec's Requirement 2 is written entirely around `PUT`, and the design's authorization discussion never mentions delete, so this is most likely an intentional scope boundary rather than an oversight. It is still worth surfacing, because a note a user cannot edit but can delete is a surprising combination; whoever owns this decision should confirm delete is meant to stay login-only. If author-only delete is later desired, it is the same one-line comparison already used for edit. (confirmed — asymmetry; intent unverified)

### Numeric `users.id` as the shared identifier, decoded client-side

The identifier is the integer `users.id`, already signed into the token as `sub` (`tokens.ts` sets `setSubject(String(user.id))`), so no server-side token change was needed — the one addition is that `decodeSession` now reads `sub`. It coerces with `Number(sub)` behind a `typeof sub === 'string'` guard, so a token whose `sub` is missing, non-numeric, or a numeric (non-string) value is treated as unreadable and returns `null`, the same way a missing `username` already is (the tests assert all three). Keeping the id in the token rather than in the login response body avoids a second identity source that could drift.

`AuthContext` widens `user` to `{ id, username }`. `ProductDetailPage` computes `canEdit = user != null && user.id === note.author` and passes `onSave` only when it holds; `NoteItem` makes `onSave` optional and renders Edit only when present, the same `{onSave && ...}` shape already used for `{onDelete && ...}`. An authorless note (`author === null`) never matches a numeric `user.id`, so its Edit stays hidden. The frontend gate is defensive UI only — a stale client that somehow shows Edit still gets a 403 from the backend.

### Test coverage

Backend coverage is strong and ran green here (202 tests across the four touched suites). The new `notes.test.ts` block covers the auth matrix (missing/malformed/empty/expired token → 401, content unchanged), the no-existence-leak property, authenticated 404, and the authorless 403, plus two 100-run property tests for author self-edit (2.1) and non-author rejection (2.2) that read the row back from the DB rather than trusting the response echo. `products.test.ts` covers that creation records the author, `database.test.ts` covers the schema and migration, and `auth.test.ts` flips its old "note edits are open" assertion to expect 401. Existing `notes.create` call sites in `database.test.ts` were updated to pass an author, using `null as unknown as number` to simulate authorless rows — a reasonable test-only cast given those tests predate the author concept.

Frontend tests were added for the same behaviors — `NoteItem` Edit visibility driven by `onSave` presence (Req 5.4), `session` decode of `sub` including the null-returning cases (Req 4.3), and `ProductDetailPage` gating across own/other/authorless notes (Req 5.1–5.3). These are well-formed by inspection but could not be executed in this environment: vitest failed to spawn its forks worker ("Timeout waiting for worker to respond"), which is an environment/pool issue, not a test failure. Run them in CI to confirm.

Not tested: there is no test asserting delete's authorization posture (that a non-author can delete a note today). Adding one would document the intended delete behavior regardless of which way the decision above goes.
