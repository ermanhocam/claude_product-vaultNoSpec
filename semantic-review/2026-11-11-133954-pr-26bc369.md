# Advanced product search with public name search and login-gated filters

This commit adds `GET /api/products/search`, splitting search into a public name filter (`q`) and advanced filters (creation-date range, note text, note author) that only logged-in users may use. The backend introduces an optional-auth middleware that attaches a user when a valid token is present but lets header-less requests through as anonymous, a validated `SearchCriteria` parser, and an injection-safe query builder that ANDs each active filter. The frontend adds a `ProductSearch` component with a debounced name field and a login-gated advanced panel, wires it into `ProductListPage` via `useResource`, and mirrors the whole contract in the MSW mock. Coverage is strong on both sides: 75 backend cases (wildcard escaping, boundary dates, impossible dates, repeated params, access control) and matching frontend integration tests.

Watch for: the advanced-filter gating leans on `hasAdvancedCriteria` treating blank filters as absent (confirmed correct, but the whole security boundary rests on it); an invalid/expired token on an anonymous-capable endpoint correctly returns 401 rather than silently degrading (confirmed); frontend `from`/`to` bounds in the mock skip date validation (possible mock/real divergence, test-only).

**Verdict**: APPROVED

## High-level view

The gating is two-layered: `createOptionalAuthMiddleware` resolves identity (absent header → anonymous, present-but-broken header → 401), and the route handler enforces authorization (anonymous + any advanced filter → 401). The fail-closed choice on a broken token means a stale session gets a clear error instead of silently losing its filters.

The query builder is parameterized throughout: user input only ever reaches SQL as a bound value, LIKE wildcards are escaped against a declared `ESCAPE '\'`, and the date range relies on the stored `created_at` being lexicographically comparable ISO-8601 UTC. Inclusive-`to` is implemented as an exclusive upper bound at the next UTC midnight, giving day-granularity inclusivity against millisecond timestamps.

Validation rejects repeated query params (Express surfaces them as arrays, the parser rejects non-strings), enforces real calendar dates via a round-trip through `Date`, applies code-point length limits consistent with the rest of the codebase, and checks `from > to` before hitting the DB.

The frontend keeps the advanced panel out of the DOM entirely for logged-out users, so the gating isn't merely cosmetic, and the API client omits empty fields so the serialized request matches the committed criteria.

### Optional-auth gating: fail-closed on a broken token

`createOptionalAuthMiddleware` (`backend/src/auth/middleware.ts`) distinguishes three cases: no `Authorization` header (or empty string) passes through with `req.user` undefined; a present header that doesn't match `Bearer <token>`, or matches with an empty token, throws 401; a well-formed header runs through the shared `attachUser`, which turns a `TokenError` into a 401 with either the expired or invalid-token message. `attachUser` is shared with the required middleware, so the two stay consistent on how token failures map to messages.

The decision that matters here is that a present-but-invalid token is rejected rather than treated as anonymous (fail-closed). The backend test `rejects an invalid token on an advanced filter with 401` confirms it: a session that expired mid-use gets "Invalid token" instead of silently dropping to anonymous access and losing its advanced filters without explanation.

```
Authorization header?
  absent / ""      → anonymous (req.user undefined) → handler
  malformed        → 401 invalidToken
  "Bearer" no tok  → 401 invalidToken
  valid Bearer tok → verify → ok: attach user → handler
                             → TokenError: 401 (expired|invalid)
```

Authorization is enforced in the route, not the middleware: `router.get('/search', optionalAuth, ...)` in `backend/src/routes/products.ts` parses the criteria and throws `unauthorized('Log in to search by date, note text or author')` when `!req.user && hasAdvancedCriteria(criteria)`. Identity resolution (middleware) stays separate from the public-vs-advanced decision (handler), keeping the middleware reusable for any "public with extras" endpoint. `/search` is declared before `/:productId` so the literal segment isn't captured as a product id.

The entire security boundary rests on `hasAdvancedCriteria` agreeing with the parsers about what counts as "set". The parsers collapse blank and whitespace-only values to `undefined`, and `hasAdvancedCriteria` checks `!== undefined`, so `?from=&to=` is treated as no advanced filter and stays public. Any future change to how a parser represents "empty" could silently open or close the gate.

### Query builder: parameterized, wildcard-escaped, range-correct

`buildSearchQuery` (`backend/src/db/repositories.ts`) only ever puts `?` placeholders into SQL; every user value is pushed onto `params`. Name terms become `p.name LIKE ? ESCAPE '\'` with the value run through `likeContains`, which escapes `\`, `%`, and `_` so they match literally against the declared escape character. The test `treats LIKE wildcards as literal characters` exercises both `%` and `_`, which is exactly where a naive LIKE filter would leak wildcard semantics to the user.

The date range exploits that `created_at` is stored as `strftime('%Y-%m-%dT%H:%M:%fZ', 'now')` — a fixed-width, UTC, lexicographically sortable ISO-8601 string. `createdFrom` becomes `>= <date>T00:00:00.000Z` (inclusive lower bound) and `createdTo` becomes `< startOfNextDay(date)` (exclusive next-midnight, making the `to` day inclusive). This is the correct way to get day-granularity inclusivity against millisecond timestamps, and the boundary test (`2026-09-30T23:59:59.999Z` excluded, `2026-10-31T23:59:59.999Z` included, `2026-11-01T00:00:00.000Z` excluded) pins it down.

Note text and author use `EXISTS` subqueries keyed on `n.product_id = p.id`, so a product with several matching notes still returns once — verified by `returns each matching product once even with several matching notes`. The author subquery compares `u.username = ?`; because `username` is declared `COLLATE NOCASE` at the column level, the equality is case-insensitive without any per-query collation, and `matches the author username case-insensitively` confirms it.

### Input validation: arrays, real dates, and range ordering

`parseSearchCriteria` (`backend/src/validation.ts`) routes each param through a shared `readQueryString` that rejects anything non-string. Because Express surfaces a repeated query param (`?q=one&q=two`) as an array, this is what produces the `must be a single string` 400 — tested directly. Dates go through `parseDateParam`, which checks the `YYYY-MM-DD` shape and then round-trips through `Date` and compares `toISOString().slice(0,10)` back to the input, rejecting both malformed (`20-10-2026`) and impossible (`2026-02-30`) dates. The `from > to` ordering is checked before the DB call and 400s with a clear message. Length limits use `characterCount` (code points, not UTF-16 units), consistent with the existing product/note validators, and the emoji-length test confirms parity.

### Frontend: gating is structural, serialization matches the contract

In `ProductSearch.tsx` the advanced panel is rendered only when `canUseAdvanced` is true, and `ProductListPage` passes `canUseAdvanced={Boolean(user)}`, so a logged-out visitor never gets the advanced fields in the DOM at all — the gating isn't just disabled styling. The name field is debounced (250ms) and live-commits only when the name is the sole changed field; the advanced fields commit on submit, so typing a note/author doesn't fire a request mid-word. `clean` trims text fields and drops empties to `undefined`, and `api.searchProducts` only sets a param when the field is truthy, so the request matches the criteria description the UI shows.

`ProductListPage` keys `useResource` on `JSON.stringify(criteria)`; the hook re-runs on `[...deps, attempt]` and intentionally excludes the inline `load` closure, so each criteria change refetches with the current closure. Creating a product while a search is active clears the filters rather than prepending a possibly-non-matching product, which avoids showing a result that doesn't satisfy the active filter.

### Test coverage

Backend covers the public path (blank/whitespace query, substring case-insensitivity, multi-term AND, newest-first, wildcard escaping, code-point length, repeated-param rejection, public-without-token), access control (each advanced filter 401s anonymously, invalid token 401s, valid token passes), date range (inclusive boundaries, open-ended from, malformed, impossible, from>to), note text (match, dedupe, no-match), author (match, case-insensitive, no-notes user), and combined filters. Frontend mirrors this through MSW with integration tests for live name filtering, logged-out behavior, advanced-panel visibility gating, and each advanced filter.

Not tested: the backend has no case asserting a blank advanced param (`?from=`) stays public — the behavior the whole gate depends on is only covered indirectly by the parsers returning `undefined`. Worth one explicit test. The MSW mock compares raw `from`/`to` strings and skips the real validation, so frontend tests can't catch a date-validation regression; this is an accepted mock/real divergence, not a product gap.
