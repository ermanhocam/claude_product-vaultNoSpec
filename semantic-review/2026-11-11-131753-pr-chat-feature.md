# Direct messaging (1:1 chat) between logged-in users

Adds a REST direct-messaging feature to Product Vault: a `messages` table with two covering indexes, a `createMessageRepository` with send/conversation/thread-summary queries, a `/api/messages` router behind `requireAuth`, body validation, and a React inbox + conversation UI that polls every 4s. The design reuses every existing convention — repository factories, `RETURNING`-based inserts, the `HttpError` helpers, `parseId`, and the `useResource` state machine — so it slots in cleanly. Authorization is enforced structurally: the caller's id is always one side of the sender/recipient pair, so there is no query path that returns another user's messages. The `PublicUser` projection keeps password hashes off the wire.

Watch for: thread ordering has no tiebreaker when two conversations' latest messages land in the same millisecond (**likely**, nondeterministic inbox order); the optimistic append in the conversation view can show a sent message twice for up to one poll interval (**confirmed**, cosmetic); and a deleted recipient is impossible today because of `ON DELETE RESTRICT`, so the "user may have been removed" 404 copy is currently unreachable (**possible**, minor).

**Verdict**: APPROVED

## High-level view

The data model stores one row per message with `sender_id`/`recipient_id` and resolves a conversation as "either direction between the pair." Both index orderings are present so neither the conversation fetch nor the thread rollup scans. Ordering is by `created_at` then `id`, which is reliable inside a conversation; the thread summary rollup drops the `id` tiebreaker at its outermost sort, so inbox order between two same-millisecond threads is unspecified.

Authorization is the strongest part of the change. Every route is behind `requireAuth`, and the repository never takes a "whose messages" parameter that isn't the authenticated caller — `req.user!.id` is hard-wired as one side of every query. The recipient id comes from the URL, but it's only ever used as the *other* participant, so there's no IDOR surface: a user can't name a conversation they aren't in, because the query is always anchored on their own id. Self-messaging is rejected with 400 and an unknown recipient with 404.

The API surface is four routes under `/api/messages`: list messageable users, list threads, get one conversation, post to one conversation. Input validation reuses `parseMessageBody` (trimmed, 1–5000 code points) and `parseId` (positive integer), matching the note/product validators exactly. Response shapes mirror the rest of the API (camelCase DTOs, `201` + `Location` on create).

On the frontend, the conversation view polls on a `setInterval` that is cleaned up on unmount and re-armed when the user or route changes, and redirects logged-out users to login. A sent message is appended optimistically and then reconciled by the next poll; because the optimistic copy and the server copy share the same id, the reconciliation is clean once the poll lands, but there is a brief window where React renders two list items with the same key.

1. **Thread ordering tiebreak** — the `/threads` rollup sorts only by `last_created_at DESC` at the outer level (repositories.ts selectThreads), so two threads whose latest message shares a millisecond order nondeterministically. Add `, partner_id DESC` (or carry the last message `id` out of the subquery and sort on it) to make inbox order stable.
2. **Optimistic append duplicate window** — `handleSend` appends the server-returned message, and the next poll returns the same message, so for up to 4s the list can render two `<li>` with the same `key={message.id}` (ConversationPage.tsx handleSend). De-dupe by id when merging, or drop the optimistic append and just `reload()` after send.
3. **Unreachable "user removed" 404 copy** — `ON DELETE RESTRICT` on `messages.sender_id`/`recipient_id` plus no delete-user route means a recipient can never vanish, so the ConversationPage 404 detail ("The user may have been removed") describes a state that can't occur today. Harmless, but worth aligning the copy with reality or noting the intended future behavior.
4. **Thread `lastBody` not truncated server-side** — `lastBody` returns the full (up to 5000-char) message body on every `/threads` response; the UI truncates to 80 chars client-side (MessagesPage truncate), so the inbox payload can be far larger than it renders. Fine at current scale; consider a server-side substring if thread lists grow.

<summary>Details</summary>

### Conversation vs thread ordering: one has a tiebreaker, the other doesn't

The conversation fetch binds the pair in both directions and orders `created_at ASC, id ASC`. Because timestamps are millisecond-precision ISO strings, two messages in the same millisecond are disambiguated by the autoincrement `id`, so transcript order is deterministic.

The thread rollup drops that safeguard. `selectThreads` partitions by "the other party" (`CASE WHEN sender_id = ?1 THEN recipient_id ELSE sender_id END`), ranks each partition by `created_at DESC, id DESC`, and keeps `rn = 1` — correct per-partner latest-message selection. But the final `ORDER BY last_created_at DESC` has no secondary key, unlike the inner window. When the newest message of two different threads falls in the same millisecond, their relative inbox order is unspecified and can vary between calls. Carry the selected row's `id` out of the subquery and add `, last_id DESC` (or simply `, partner_id DESC`) to the outer sort to make the inbox deterministic.

### Authorization and IDOR: anchored on the caller, no leak path

```
GET/POST /conversations/:userId
  partner = requirePartner(:userId, req.user.id)   // 400 self, 404 unknown
  read:  findConversation(req.user.id, partner.id) // caller is always one side
  write: create(req.user.id, partner.id, body)     // caller is always sender
```

The recipient id is attacker-controlled (it's in the URL), but it's only ever used as the *partner*, never as the identity whose messages are read. There is no route that accepts "show me user X's threads" — `/threads` and the conversation read both derive the owning id from `req.user!.id`, which comes from the verified token. So a user cannot read or inject into a conversation they aren't part of: the worst they can do with an arbitrary `:userId` is open or start *their own* conversation with that user. `requirePartner` rejects self-messaging (400) before the recipient lookup and returns 404 for an unknown or non-numeric id. This is the right posture and the isolation test (`does not leak messages from unrelated conversations`) locks it in.

One behavioral note on `requirePartner`: a non-numeric `:userId` makes `parseId` return `undefined`; the `id === selfId` check is then `undefined === number` (false), and the subsequent `id === undefined ? undefined : findById(id)` yields `undefined`, so the route returns 404. That's a sensible outcome, though a malformed id arguably fits 400 better than 404 — the existing product/note routes resolve `parseId` the same way, so this is consistent with the codebase rather than a new inconsistency.

### Secret handling and injection surface

Users reach the client exclusively through `toPublicUser`, which projects `{ id, username }` and drops `passwordHash`; the `/users` test asserts the exact shape, so a future field added to `User` won't silently leak into a message or thread response. `parseMessageBody` reuses `readRequiredText` and its 5000-code-point cap matches the DB `CHECK (length(body) BETWEEN 1 AND 5000)`, so an oversized body is rejected at the edge rather than by a constraint violation. Every message query uses bound parameters — no user value is interpolated into SQL.

### Optimistic append can duplicate against the poll

The poll interval keys on `[user, reload]` with `reload` a stable `useCallback`, so it's cleaned up on unmount and doesn't re-arm every render, and `useResource` keys on `[userId, user?.id]` so switching conversations refetches — the lifecycle itself is sound.

The rough edge is reconciliation. `handleSend` appends the server-returned `Message` to local state, and the 4s poll independently refetches the full transcript, which already contains that message. Once the poll lands, React sees two entries with the same `key={message.id}` for that render pass. Because both copies carry the real server id, merging with a de-dupe on id (or dropping the optimistic append in favor of `reload()`) removes the duplicate-key window.

### Test coverage

Backend coverage is solid: auth required on every route, send happy-path with the exact DTO and `Location` header, trim/empty/oversized body, self-message 400, unknown-recipient 404, transcript order in both directions, cross-participant symmetry, cross-conversation isolation, and the thread summary/ordering. 

Not tested: two messages created within the same millisecond (the ordering tiebreaker that the thread rollup lacks) — this is exactly the untested case that would surface issue #1. Not tested: the frontend polling/optimistic-append reconciliation (no test asserts the list doesn't duplicate after a poll following a send). Not tested: a non-numeric `:userId` resolving to 404 (the `requirePartner` undefined path).
